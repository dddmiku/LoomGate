# 工作台版本的一键更新与旧版恢复

工作台的任务引擎、任务凭据库和推理凭据库各自持有进程级排他锁。旧进程仍提供服务时，新进程不能同时打开这些状态。原来的更新流程等待新进程报告就绪后才停止旧进程，因此从过渡版继续升级时，新进程会以 `task already has an active lease` 或 `vault_busy` 退出，更新保持失败。

## Linux 受监督容器的一键更新

在现有 docker-entrypoint.sh 启动并监督的 Linux 容器中，启用工作台的网关使用以下流程：

1. 从配置的更新源读取目标，下载并按发布公钥验签、校验 SHA-256。完整运行包还要通过成员、架构、清单和摘要校验。
2. 复制公网与管理监听器，停止接收新任务，等待在途 HTTP 请求和任务收尾，再释放任务引擎与凭据库的排他锁。
3. 自动启动候选版本，继承原监听器和启动参数。候选报告就绪后，核对运行版本及管理入口，再原子提交 `current` 启动指针。
4. 界面自动重连并读取运行状态；只有目标版本实际运行才显示完成。若候选启动或核验失败，程序自动启动保留的旧版本，恢复服务并显示更新失败。

正常更新点击一次“立即更新”即可。提交采用同步预占，浏览器在连接中断后只读查询，不重复发送应用请求；旧的浏览器提交保护会随实际服务状态恢复，不再要求人工解除或填写确认表单。

切换期间可能短暂无法访问，页面会自动重连。排空等待有超时上限，不能据此保证任意时长的对话永不中断。更新结果通过固定恢复记录跨进程保留；下载完成或回到空闲均不能单独证明目标版本已运行。

下载、验签或解包失败时当前服务继续运行。候选切换失败后尝试恢复真实旧进程；若候选与旧进程均无法启动，或恢复启动指针失败，状态会明确报告恢复故障，保留所需更新文件供维护处理。

## 平台与启动方式边界

自动顺序切换需要启动链能够接管后继进程。Linux 容器沿用现有 PID 1 启动脚本即可识别此能力；任意未受监督的启动方式不会宣称支持自动切换。Windows 和未满足条件的启动链继续验签暂存，返回 `restart_required=true` 与 `staged_version`，由启动器或维护者重启网关后生效。Android 沿用同签名 APK 与系统安装器。此处的重启仅指网关进程或容器，不需要重启计算机。

完整运行包通过全部校验后才生成固定所有权标记。清理仅处理带有效普通文件标记的受管理目录，同时保护实际运行目录与待启用目录，连续升级保留两个受管理运行目录。没有标记的旧版存量和用户目录保留；标记为链接或内容无效时也不删除。

## 已安装 v1.0.5 / v3.17.0 的第一次恢复

这些已安装的旧二进制仍包含原来的交接逻辑。仅发布一个新目标包，无法改变旧进程在启动目标之前执行的更新流程。新版提供一次性恢复命令，在旧服务仍运行时直接准备下一次启动所需的完整运行包，避开旧发送端等待新任务引擎就绪的循环。

恢复程序应从带原发布签名身份的正式新版安装包或运行包获取；测试构建使用独立测试公钥，不能用于真实部署。恢复命令要求二进制内置有效发布公钥，没有公钥会明确拒绝，绝不以开发构建的免验签行为兜底。由于恢复程序本身可能就是目标版本，同标签恢复允许下载并校验该版本。

在原部署的容器或相同文件系统中执行下面的命令。/absolute/recovery/wb2api 是可信新版程序的绝对路径，配置与更新目录也必须替换为原部署真实的绝对路径。不要从新解包目录推测原服务的工作目录。

    /absolute/recovery/wb2api -repair-update \
      -config /absolute/existing/config.json \
      -repair-update-dir /absolute/existing/data/updates

    /absolute/recovery/wb2api -repair-update-status \
      -config /absolute/existing/config.json \
      -repair-update-dir /absolute/existing/data/updates

Windows 使用同平台的 wb2api 程序执行相同参数，并提供 Windows 绝对路径；Android 沿用同签名安装器覆盖安装。不能将 Linux 程序或更新包用于其他平台。

命令输出只包含修复状态、目标版本及下一步提示。state=staged 和 restart_required=true 表示发布签名、完整运行包与下一次启动指针已准备好，当前服务仍继续运行。状态查询不打开账号库和任务引擎；重复准备同一修复不会重复下载。它不会自动终止进程、重启容器或重启计算机。安排维护窗口重启网关或容器后，从运行服务核验版本及健康状态。

恢复期间关闭旧界面的更新操作，避免同时应用两个更新。恢复命令自身使用排他锁串行化，但旧版发送端并不参与该锁。回滚执行前会比较当前指针与本次修复候选，并重新验证原运行包和候选的完整摘要；这不是与旧版更新器之间的跨进程原子事务。

需要恢复修复前的启动指针时，执行：

    /absolute/recovery/wb2api -repair-update-rollback \
      -config /absolute/existing/config.json \
      -repair-update-dir /absolute/existing/data/updates

如果指针已经被其他更新改动、原运行包或候选文件发生变化，回滚会拒绝覆盖，保留现场。回滚仅恢复启动指针，不会终止已经运行的进程。修复记录固定保存在更新目录的 transition-repair.json，只保存路径、版本和摘要，不保存配置或凭据；不按时间戳无限追加备份。

切换前保留当前运行包、配置和数据目录；切换后核对运行版本、健康检查以及账号、密钥、用量和任务状态。如果新实例未通过启动与健康核验，恢复原启动指针并使用保留的旧运行包。账号和凭据数据沿用原目录，避免重新初始化。

上述一次恢复完成后，支持自动切换的 Linux 容器可在界面一键完成后续升级；其余平台按实际状态提示启用。旧二进制仍需这一次过渡，发布新包无法改写正在运行的旧发送端逻辑。已知旧更新源在运行时只读映射到 LoomGate，保留自选镜像且不提前重写旧配置。此文档描述恢复方法，不表示当前部署已经更新或已经执行重启。

## 回归验证

`internal/hotupdate/staged_update_test.go` 在本地签名发布 fixture 上验证：单文件和完整运行包可提交、当前 HTTP 仍响应、任务与凭据库所有者锁仍由旧实例持有、待启用目录不被清理、重复提交被拒绝、指针提交失败时回收未提交目录。

控制台与旧面板的更新卡和流程测试覆盖单次提交、断线重连、旧提交保护恢复、实际运行目标核验和平台暂存提示。Linux 顺序切换测试覆盖真实监听器、排他状态锁、候选崩溃与健康核验失败回滚，以及启动指针和恢复记录的 I/O 故障。完整容器链需额外通过真实 main、非 root 与旧 PID 1 启动脚本验收，不能只用组件测试替代。

repair_test.go 与入口子进程测试覆盖强制验签、同标签恢复、指针和整包摘要检查、旧状态所有者锁保留、重复准备、回滚冲突、目录边界、中断准备及操作互斥。恢复命令的状态只描述记录和启动指针，不作为实际运行版本的证据。
