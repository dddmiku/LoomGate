# 版本号规则

本文件是所有发布动作的唯一依据。改版本号前先读这里，不要凭印象递增。

## 格式

`vMAJOR.MINOR.PATCH`，与 git tag 完全一致（含 `v` 前缀）。

构建脚本只接受该形式：`build_acceptance.py --version vX.Y.Z` 会用正则
`v(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)` 校验，不符合直接拒绝构建。
代码里不出现 `v1.0`、`1.0.1`、`v1.0.1-beta` 这类变体。

## 何时递增哪一位

| 变化 | 位 | 例子 |
|---|---|---|
| 用户可见的不兼容变更：配置格式、协议契约、数据布局、需要迁移才能继续用 | **MAJOR** | 旧配置不再被读取 |
| 新增能力：新 provider、新协议、新任务、新页面 | **MINOR** | 加了 AutoClaw 渠道 |
| 缺陷修复、性能改进、文案修正，行为对调用方保持兼容 | **PATCH** | 修一个 502、修一次登录 |

判据是**调用方要不要改**，不是改了多少行。一次改动横跨几十个文件，只要外部
契约不变就是 PATCH。

## 三条硬规则

1. **中间改动不动 VERSION。**
   `gateway/VERSION` 只在正式发布那一个点上改。开发期间的构建一律
   `--version dev`，commit 由构建期注入，面板与 `/healthz` 显示真实提交。
   禁止"先把版本号改上去再慢慢修"。

2. **一个版本只发一次。**
   `v1.0.1` 发布后即使发现缺陷，也发 `v1.0.2`，不复用已推送的 tag。
   tag 一旦推送就意味着"这个版本的资产已签名并对外"，重打会破坏信任链。

3. **资产与声明必须一致。**
   Release 的 tag、`version.Version` 注入值、资产文件名、`SHA256SUMS.txt`
   四者版本号相同。构建后用 `--loomgate-build-info` 核对实际产物里的
   version/commit/platform，不靠文件名推断。

## 开发标记

| 场景 | version 注入值 | 面板显示 |
|---|---|---|
| 本地/CI 开发构建 | `dev` | dev + 真实 commit |
| 正式发布 | `vX.Y.Z` | 版本号 + commit |

`internal/version.IsDev()` 据此判断，自更新对 dev 构建会提示但仍允许。

## 发布前的固定动作

1. 确认目标提交的 `go test ./...`、`go vet ./...`、控制台 JS 测试全绿。
2. 改 `gateway/VERSION` 为目标版本，写 `gateway/CHANGELOG.md` 条目。
3. 用 `--version vX.Y.Z --commit <sha>` 构建全部目标平台。
4. 对产物运行 `--loomgate-build-info`，核对版本/提交/平台/公钥摘要。
5. 生成 `SHA256SUMS.txt`，用发布私钥签名。
6. 推 tag → 创建 Release → **确认附件齐全且可下载**。
   只上传 workflow artifact 不算发布。
7. 回读 Release：附件数量、每个 URL 的 HTTP 200、hash 与本地一致。

## CHANGELOG 写法

条目只写"改了什么、为什么"，面向使用者，200–430 个字符量级。
不写内部实现细节、不贴账号/手机号/令牌等任何真实数据（示例必须是假值）。
禁止出现"应该""可能已修复"这类不确定表述——没验证的不写进 CHANGELOG。
